## Growth, CRM, analytics and AI release gates

The review used backend main `e07fb78`, storefront main `fa8a928`, backend push and visual-search PR #6 `8e61075`, and WhatsApp and inbox PR #16 `cab77b1`. “Implemented” below describes repository behavior. Live account settings, campaign spend, consent records, customer devices, provider receipts and production traffic were not inspected.

| Capability | Implemented and verifiable | Release blocker or missing work |
| --- | --- | --- |
| CRM and repeat customers | Backend draft #36 connects admin-only customer detail and the current storefront's directory filters. Local MongoDB and HTTP tests verified the storefront's actual list/detail validators, order ownership, denial for customer/supplier accounts and the existing status mutation. Repeat means at least two orders with an eligible confirmed status after excluding recorded test/demo orders. | Review and deploy #36 to the paired staging environment. These administrative records supply neither promotional consent nor a marketing audience. |
| Product discovery and organic SEO | The build generates canonical product documents, sitemap and structured data. Stock and price watches compare the current catalogue to a saved device watch. Fitness recommendations use local product matching and availability rules. | Search Console property access and actual impression/click data are needed to measure indexing and performance. Price/stock watches do not have an email or push delivery path. The recommendation rules do not establish personalized lift. |
| Google Analytics | Web-only GA4 initialization requires a valid `VITE_GA_MEASUREMENT_ID` and an explicit grant. Ad storage and ad personalization are denied. | On main, a previously opted-in tab still queued an event after withdrawal in another tab. Storefront PR #81 fixes it. Local two-tab Chromium checks passed with all external requests blocked, as did 285 storefront tests. Merge the fix and verify the intended consented events in the authorized GA property. |
| Meta measurement and catalogue | Backend routes expose preferences, attribution, shopping events, verified order events, catalogue refresh and diagnostics. The worker checks consent and configuration before CAPI delivery. Eligible feed products require admin advertising review. | Default flags are off. No consumer of the Meta preferences/event endpoints or browser Pixel loader was found in storefront main. Wire and test the customer consent UI across grant and withdrawal before enabling browser tracking. Verify dataset ID, allowed events, product eligibility, policy review, `META_CAPI_ACCESS_TOKEN`, test-event code, matching browser/server IDs and confirmed provider receipts. No live ROAS or attribution coverage was verified. |
| Transactional order updates | Backend #16 and #25 can derive owned in-app messages directly from saved order and after-sale facts. #16 has per-order WhatsApp opt-in, revocation, a sender and signed status callbacks. Backend #6 has account-owned device registration, outbox, delivery stop control and opt-out for native push. | In-app acceptance is independent of external delivery. WhatsApp requires its two launch flags, approved template and sender, verified webhook, authorized test recipient and an approved cost. Native push requires explicit user/device permission, registration and delivery flags, database enablement, token encryption key and correct APNs/FCM configuration. Verify delivery and revoked-device behavior on real devices. These consents cover order alerts only. |
| Promotional email, lifecycle and loyalty | A Gmail OAuth sending helper exists. No caller of that helper was found on backend main. Existing product watches, order alerts and customer search each have a narrower purpose. | No end-to-end campaign enrollment, channel-specific promotional consent, suppression/unsubscribe, cart-abandonment or win-back scheduler, referral attribution, or reward ledger was found in the reviewed paths. Implement and rehearse these before sending. Channel owner, recipients, retention, incentives, budget and approved provider configuration remain open. |
| Paid ads, content and partnerships | Meta can prepare an approved catalogue and measure events. Static campaign artwork and factual product pages already exist. | No campaign/ad-set budget mutation, creative publishing, influencer outreach, partner commission payout or Google Ads buying connector was found. Define channel owners, rights, budget caps and approved attribution inputs. Prepare drafts and previews before connecting paid accounts or publishing. |
| AI shopping, support and forecasting | Backend #6 implements local photo similarity using a catalogue vector snapshot. The storefront has a fitting-room prototype with approved assets, explicit photo consent and FASHN request caps. | Search requires an installed pinned model, refreshed catalogue index, tested host memory and independent photo evaluation. Try-on requires eligible imagery, approved third-party processing, funded credentials, cost controls and a deployed service. No autonomous AI support agent, independently measured demand model, or supplier-performance predictor was established. Account for missing delivered-order, return, stockout and cost history before evaluating forecasts. |
