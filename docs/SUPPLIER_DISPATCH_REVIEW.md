# Supplier dispatch review

The supplier portal's marketplace API can flag an open fulfilment when a purchased line with remaining quantity exceeds its agreed dispatch window. Call `GET /api/marketplace/dispatch-review` with a signed-in supplier account, or use `?supplier=<account id>` as an active admin. A supplier can see only the active marketplace workspace they own. The endpoint returns read-only review rows. It sends no messages and takes no fulfilment or financial action.

**Optional contract term.** Existing agreements specify preparation days but do not establish a clock. Only after the owner and supplier agree to the exact basis, the existing commercial-terms workflow may carry `dispatchClock: "elapsed-days-from-payment-verification"`. This means the deadline is the recorded payment verification time plus the purchased maximum preparation days, with each day equal to 24 elapsed hours. At the deadline the order is still within its window. This basis includes weekends and holidays. Workday calendars, cutoff times, courier delivery promises and unverified COD payments have no inferred deadline here. The new property has no default. Changing it alters the terms digest, requires fresh supplier acceptance and admin approval, and applies only to subsequently purchased listings on the accepted terms. No existing agreement, listing, purchase or order is backfilled.

Only pending, accepted or preparing supplier groups with confirmed or processing orders and recorded paid/partially-paid/partially-refunded status enter evaluation. The assessment uses each purchased line's account, original signed-off terms snapshot and digest, remaining quantity after cancellations, and the order's verified payment time. An overdue known line flags the group. An ambiguous line prevents an all-clear when no known line is overdue. Unknown-only groups do not generate overdue alerts. The response exposes identifiers, group status, earliest known due time, classification and missing-line count. Current supplier settings, customer addresses, customer identities and free-text contract evidence are excluded.

Use `source=real` or `source=test`; the default is real. Orders missing the explicit demo flag are excluded. Each page examines up to 50 active fulfilment candidates for the selected supplier. Apply `after=<nextCursor>` until it returns null, including after empty filtered pages. The cursor follows ascending fulfilment ID and status can change between requests. Dates in the response use UTC. Rows describe the current state. Re-reading an unchanged purchase yields the same deadline and fulfilment identifier.

**Release.** Approve the proposed clock wording before enabling it in the supplier terms UI. Use the existing protected acceptance, listing approval and republishing process. Verify `db.marketplacefulfilments.createIndex({supplier:1,status:1,_id:1})` on an approved staging database. The route requires the index, times the query out after five seconds, and caps each lookup page. Startup performs no migration. An existing marketplace database may already have the collection. The referenced orders use their default unique ID index. Review integration evidence from `node tests/integration/dispatch-review.cjs` in an explicitly named loopback fixture and the unit tests. No scheduler, automatic penalties, customer delivery promises or production activation are included.
